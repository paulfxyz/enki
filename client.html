Plug-ins & connectors

Explore documented APIs, actions and MCP support where the platform permits them. Running a tool at home does not make the cloud conversation private; returned data may still reach the provider.

Open forks

Prefer upstream contributions and supported provider adapters. Maintain a fork only where the licence permits it and the maintenance burden is justified.

SDK & standard

A versioned inference API, separate MCP tools and client libraries are proposed deliverables. Integration effort depends on the client and security requirements, not a five-line promise.

The targets

Named clients,
named plans.

ChatGPT

Proposed: an authenticated Actions bridge, subject to supported interfaces and platform terms. ChatGPT still runs in the cloud; prompts and tool results may be processed there. Local execution is not local-only privacy.

Perplexity

Proposed: a connector for permitted research workflows. Any excerpts returned to a cloud research service leave the mesh; the user must see and approve that boundary.

OpenAI & Meta agents

Explore documented tool interfaces on a platform-by-platform basis. A delegated task may execute locally while its result returns to a cloud agent. No working integration is claimed.

Gemini

Explore supported Android and Gemini integration paths. Platform support, permissions and data flows need validation before promising a particular voice command or private route.

Claude Code

Proposed: a local MCP server exposing approved mesh tools. Claude Code may still use hosted inference and transmit tool results; zero cloud round-trips requires a fully local client and model path.

LibreChat & open UIs

Prioritise provider adapters and upstream contributions for compatible open UIs. A maintained Enki fork or accepted upstream change is not yet claimed.

iOS & Android

Proposed native clients and share-sheet support. Remote mesh access would need authenticated tunnelling, key management and an explicit exposure policy; it is not enabled today.

Echo & speakers

Explore supported voice integrations, but many speakers use cloud speech processing. An Enki skill would not turn an existing cloud speaker into a fully local microphone.

Everything else

Proposed: public conformance tests and a Mesh Ready programme. No client is certified by Enki today; the badge must follow a published test process.

The plan

A proposed delivery sequence.

  1. Freeze the endpoint spec, v1. One OpenAI-compatible surface at localhost:1134/v1 plus discovery — published, versioned, boring on purpose.
  2. Ship the SDKs. TypeScript, Python, Swift, Kotlin — each with a five-line quickstart and a reference app.
  3. Ship the MCP server. Claude Code, agents and IDEs see the mesh as tools on day one.
  4. Release the plug-in pack. ChatGPT, Perplexity, Gemini and the agent stacks — one install page, each kept current by a named member.
  5. Maintain the forks. LibreChat first, then the next most-used open clients — thin forks, loud upstream PRs.
  6. Open Mesh Ready certification. A public test suite; pass it and your client carries the badge. The registry lists every certified client.

An owner-controlled endpoint reduces dependence on any one client. Platform-specific integrations still depend on platform support, terms and data handling. The default we should build is a genuinely local path, with cloud connections explicit rather than hidden.

Worth building

The Context Vault — your memory, staying home.

The proposed vault would make selected context portable across compatible clients: an encrypted store, explicit access grants and documented export. Local retrieval is not a guarantee that an app cannot retain the excerpts it receives.

CV · 01Local storeProposed: an encrypted local store and vector index for selected notes, preferences and facts, with documented export and backup.
CV · 02Local embeddingsProposed: compatible embedding models build the index on-device. Quality, memory use and supported languages need testing.
CV · 03Sealed at restProposed authenticated encryption, with hardware-backed protection for keys where available. Exact algorithms, key wrapping and recovery require platform-specific validation.
CV · 04Scoped grantsProposed per-app scopes, readable access logs and revocation. Revocation stops new requests; it cannot erase copies already obtained.
CV · 05Retrieval, not uploadRetrieve only authorised excerpts, then disclose where the chosen model runs. Sending an excerpt to the cloud is still a data transfer.
CV · 06HandoffTarget: an encrypted, documented export that compatible clients can import. Versioning, key recovery and migration need implementation.

The Context Vault — the concept, in full

The problem it solves

Useful context can become a switching cost when it is tied to one provider. The vault aims to reduce that dependence with a documented, local data format. Storage location alone does not prevent lawful access, malware or disclosure through an authorised client. The design must account for those paths.

The store

The proposed store combines structured records and a local retrieval index. Entries would carry provenance, timestamps, scopes and correction history. Storage grows with source material, embeddings and model files; no universal “hundreds of megabytes” footprint is established.

The seal

Authenticated encryption at rest is a design requirement. Where available, hardware-backed keys could protect a wrapped data key; bulk encryption may occur outside the secure hardware. The algorithm, platform support, passphrase derivation, backup and recovery paths need implementation review. Encryption does not protect an unlocked, compromised session.

The grants

Clients would request narrowly defined scopes, with local audit logs and revocable grants. Revocation blocks future access but cannot claw back data a client already saw or copied. Sensitive actions need separate approval; permission to read a note must not silently become permission to publish or delete it.

The retrieval path

Retrieval would run locally and supply only approved excerpts. An authorised mesh node still receives those excerpts; a hosted client or model would receive them outside the local boundary. The design should minimise disclosure, make the destination visible and keep external transfer opt-in. Encryption at rest does not conceal plaintext from the model processing it.

The handoff

A documented encrypted export is a design goal, not a released format. Moving to another device or leaving Enki should preserve provenance and permissions without requiring an Enki account. Recovery, backup, deletion and duplicate-copy handling remain part of the specification to be written.

Status: concept. These are proposed requirements, not a released vault, audited cryptographic implementation or confirmed active prototype. A documented format and threat model must precede security claims.
